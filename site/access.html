Access

This site is allowed to show aggregates

The public page and the Ask box use the metric catalog. They do not load dim_user. An analyst who needs a person-level row uses the model files under a separate permission, and still does not put those columns into a metric.

ColumnWhere it livesWho can see it
user_namedim_userRestricted. Not in any mart, metric, or page on this site.
emaildim_userRestricted. Ask refuses a request for an address.
age_band and age_band_rawdim_userRestricted. The column includes a 13–17 band, so the whole column stays off the site.
is_test_accountUser dimension and both factsVisible to the build. Metrics keep only false.
Metric totalsmetrics/*.yml and this siteAnyone who can open the page. Counts and distinct people, never a person.
Dashboard aggregatessite/data/cubes/*.jsonAnyone who can open the page. Each file holds a metric’s counts for every combination of the dimensions its file allows. There are no user_id values and no row-level data.
Small counts of peoplesubscribers_active cubeA distinct-people cell with fewer than 5 people is published as blank and shown as “<5”. Counts of subscriptions are not suppressed because they do not describe a person.

What a row-level role would add

A named analyst could open fct_subscription and dim_user to audit a duplicate or a sentinel. That role still cannot publish email or age_band through Ask. The interface has no metric whose grain is a person.

Test accounts remain in the fact tables with is_test_account = true so the exclusion can be checked. They are already gone from the numbers on the dashboard and Ask.

Publishing this folder does not publish the raw files or dim_user.csv. Those stay outside site/.
