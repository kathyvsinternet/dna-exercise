# Project Documentation

This file is a run-down of the structure of this project and key decisions that were made. This page can serve as a pre-read to the live presentation and demo.

## The Concept

After reviewing the prompt, recorded in the [README](README.md) of this project, I decided to build a reporting dashboard from scratch and deploy it into a microsite, so the whole project can live in one place. As I am nowhere near an expert in front-end web development, the bulk of this microsite and its functionality was built by the Cursor AI agent.

The models that Cursor employed were largely Claude Sonnet 5.5 and Haiku 5.5. Sometimes the agent auto-balance would select the Grok 4.7 model. For the site build and underlying data manipulation, I would occassionally edit Python, HTML, YML, and CSS scripts. The bulk of my **human-written** code is found in [/data/marts/sql/](/data/marts/sql/), where I keep the SQL code for intermediate and mart models. The SQL powers the static mart CSVs that are written with each build.

## Ensuring Data Quality

All of the raw CSVs from the provided Google Drive folder were uploaded into [/data/raw/](/data/raw/). The agent then read through the files and identified data quality issues. It documented the issues in [/data/quality/issues/](/data/quality/issues/) and also recommended a treatment for each file. With each pipeline build, the project then applies these treatments to the relevant files and outputs cleaned CSVs into [/data/model/](/data/model/), adopting a `dim_*` and `fct_*` naming convention for these models.

The [checks.py](/pipeline/checks.py) script fails if the issues persist.

## Building Data Models

Downstream of these cleaned CSVs, the intermediate and mart models within [/data/marts/sql/](/data/marts/sql/) determine which data marts power the dashboard. With the exception of the `mart_user_share_*` CSVs, all of the [/mart/](/data/marts/) CSVs were generated directly from the data models.

These `mart_user_share_*` marts are generated by running [eph_user_info.sql](/data/marts/sql/eph_user_info.sql), [user_share.py](/pipeline/user_share.py), and then [build.py](/pipeline/build.py). The comments in the ephemeral model describe this process. 

## Protecting Access

The [schema.yml](/data/model/schema.yml) file documents the schema of each of the reporting marts. This file marks `user_name` and `email` as restricted such that this data is never displayed in reporting. Currently `age_band` is not restricted, but with a more complex data project that supports deeper model joins, it may be prudent to make this data unavailable except for at the broadest cuts.

The microsite dashboard only receives aggregate data and reads from the JSON files in [/site/data/marts/](/site/data/marts/). So the public stie does not have any access to deeper underlying models.

We use `user_id` to do a distinct count of users but the values are never shown. Any distinct count of users below 5 is not meant for the publich page. The **two exceptions** here are "Users by Active Subscriptions" and "Users by Paid Subscriptions".

## Guarding Against Agentic Hallucinations

Instead of letting the AI chat bot go wild, the [chat.py](/pipeline/chat.py) and [executor.py](/pipeline/executor.py) scripts guard responses heavily. The chat will only provide answers from a fixed set of published marts through its query tool. Any numerical reply must match an approved value or the chat will tell end users that they cannot provide a verified answer to the question.

## Publishing the Dashboard

In order to create the microsite of the dashboard in production, I took advantage of [Github Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site), used Google AI Studio's free tier to create a Gemini API key, and opened a free Vercel account to host the AI chat backend.
